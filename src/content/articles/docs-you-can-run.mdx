circlekit is a Python SDK for x402 payments through Circle Gateway. I ported it from TypeScript to Python, and until now it had no docs beyond a README and a few examples. This article shows how I built its docs site with [Thally](https://www.thally.io), a framework for documentation sites, and how running the code on its pages helped me spot a bug: payments made with circlekit's default settings were rejected by Circle Gateway.

If these names are new to you, here is what they mean:

- **[x402](https://www.x402.org)** is a protocol that lets a program pay for an API call on its own. It reuses the HTTP status `402 Payment Required`: the server answers `402` with a price, and the client signs a payment and sends the request again. The client that pays is the buyer; the API that gets paid is the seller.
- **[USDC](https://www.circle.com/usdc)** is a stablecoin: a digital token on a blockchain whose value is tied to the US dollar (Circle, which issues it, says it can be redeemed 1:1 for dollars). Because it lives on a blockchain, a program can pay with it directly, with no card or bank account.
- **[Circle Gateway](https://developers.circle.com/gateway-nanopayments)** is Circle's USDC payment service. The buyer deposits USDC into it once, and Gateway checks each payment and pays sellers in batches instead of one blockchain transaction per payment.
- A **testnet** is a test copy of a blockchain, where tokens have no real value and you get them free from a [faucet](https://faucet.circle.com). circlekit's examples run on Arc Testnet, the testnet of [Arc](https://docs.arc.io), Circle's blockchain.
- A **wallet** is an address plus a private key. The buyer signs payments with its key, and the seller receives them at its address.

The SDK's source is at [vyperlang/circle-titanoboa-sdk](https://github.com/vyperlang/circle-titanoboa-sdk): the package is named `circle-titanoboa-sdk`, is installed from GitHub, and is imported as `circlekit`.

The source code for the docs website can be found at
[github.com/lufa23/circlekit-docs](https://github.com/lufa23/circlekit-docs).
To build a docs site like it with Thally, follow the steps below.

## What you need

Node.js (I used 22), Python 3.10 or later, `git` and `curl`, plus `rsync` for step 7.
No wallet or keys are needed.

## 1. Scaffold the site

First, scaffold the site:

```bash
npx --yes create-thally-docs@latest circlekit-docs --yes --install
cd circlekit-docs
```

The `--yes` flag accepts the default answers and `--install` installs the dependencies.
After about a minute, you get a Next.js project.

You only need to edit four places (step 5 adds a small `tools/` folder for checks):

| Path | What it holds |
|------|---------------|
| `src/content/` | the pages, as MDX |
| `docs.json` | tabs, sidebar groups, and the API reference source |
| `src/data/site.ts` | product name, header and footer links, and colors |
| `openapi.yaml` | the API description behind the API reference |

Most of the rest belongs to the Thally runtime. `starter-release.json` lists which files
the framework updates for you, so leave those alone.

## 2. Plan the pages around what the reader does

Developers interested in circlekit are mainly Python developers who want to charge for an API, or want their agent to pay for one. For this reason, the docs site has three parts:

- a **Quickstart**, where no wallet is needed. This lowers the onboarding friction: you run a paid endpoint and read its `402` reply,
- a **guide** that makes a real payment with test money on Arc Testnet,
- an **API reference** for the example endpoint.

The project that `create-thally-docs` generates (Thally calls it the starter) comes with
sample pages. Remove the ones you will not use. The starter's API overview suggests
rewriting its Authentication page rather than deleting it. On the circlekit docs website I rewrote it, but
for this walkthrough I wanted the API tab to have one page, so I removed it:

```bash
rm -r src/content/guides src/content/components.mdx src/content/customization.mdx \
  src/content/changelog.mdx src/content/api/authentication.mdx
```

You can then open `docs.json` and replace its `tabs` array with the navigation for the remaining pages. You can leave the other keys as they are:

```json
"tabs": [
  {
    "tab": "Get started",
    "groups": [{ "group": "Get started", "pages": ["introduction", "quickstart"] }]
  },
  {
    "tab": "API Reference",
    "groups": [{ "group": "Overview", "pages": ["api/introduction"] }],
    "api": { "source": "openapi.yaml" }
  }
]
```

To get an API reference, you only need the `api.source` line. Thally reads `openapi.yaml` and adds a page per operation to that tab. Once you replace the spec in step 4, that page will be `/api/default/forecast/get`.

Because some of what is left still links to the pages you just removed, you need to run the checker:

```bash
npx --yes @thallylabs/cli@latest check
```

It reports two broken links in the homepage, `src/content/introduction.mdx`: the
`<Card>` links to `/customization` and `/guides/create-a-site`. Delete those two `<Card>`
blocks. Three more links point at removed pages, and the checker does not report them:

- `secondaryHref="/guides/create-a-site"` on the `<Hero>` near the top of the homepage.
  Point it at a page you keep and change `secondaryLabel` to match, for example
  `/api/introduction` and "API reference". The homepage text is still the starter's,
  so rewrite it for your product while you are there.
- The `Changelog` entry in the `links` list of `src/data/site.ts`, which becomes the
  footer link on every page. Delete that line.
- A link to `/api/authentication` inside a `<Note>` in `src/content/api/introduction.mdx`.
  That page also still describes the starter's sample API, so replace the whole file:

```mdx
---
title: API overview
navTitle: Overview
description: The request and response format of the x402-protected example endpoint.
---

This reference documents the Weather API from the [Quickstart](/quickstart). This is one
endpoint, `GET /forecast`, priced at $0.01 per request.

| Request | Response |
|---------|----------|
| No `PAYMENT-SIGNATURE` header | `402` with the payment options |
| Valid, funded `PAYMENT-SIGNATURE` | `200` with the content |
```

Run the checker again; it should print `No issues found.` Because it missed three links,
step 7 also checks the built site's links.

## 3. Write the Quickstart with named code blocks

Thally pages are MDX with built-in components such as `<Steps>`, `<Note>` and
`<Accordion>`. On top of those, one habit matters most here: give every code block the
reader saves to a file a title, which is the file name:

````text
```python title="server.py"
````

The title shows above the block on the site, and in step 5 a short script uses it to
pull the code out and run it.

Replace `src/content/quickstart.mdx` with this shortened version of the circlekit
Quickstart:

````mdx
---
title: Quickstart
description: Run a paid API endpoint locally and read the 402 response a paying client receives.
---

Run a FastAPI endpoint that charges $0.01 per request, then decode the payment
requirements it sends back. No wallet or keys needed.

<Steps>
  <Step title="Install circlekit">
    circlekit is installed from GitHub; it is not on PyPI.

    ```bash
    python3 -m venv .venv && source .venv/bin/activate
    pip install "circle-titanoboa-sdk[examples] @ git+https://github.com/vyperlang/circle-titanoboa-sdk@1a05260ff83756fb3db1ad75ee0263c70127bf22"
    ```
  </Step>
  <Step title="Write a paid endpoint">
    ```python title="server.py"
    import os

    from fastapi import FastAPI, Request
    from fastapi.responses import JSONResponse
    from circlekit import create_gateway_middleware

    app = FastAPI(title="Weather API")

    gateway = create_gateway_middleware(
        seller_address=os.environ["SELLER_ADDRESS"],
        chain="arcTestnet",
        description="Weather API",
    )


    @app.get("/forecast")
    async def forecast(request: Request):
        result = await gateway.process_request(
            payment_header=request.headers.get("PAYMENT-SIGNATURE"),
            path=request.url.path,
            price="$0.01",
        )

        # No payment, or a rejected one: return the 402 body and headers.
        if isinstance(result, dict):
            resp = JSONResponse(result["body"], status_code=result["status"])
            for k, v in result.get("headers", {}).items():
                resp.headers[k] = v
            return resp

        # Paid: return the content plus the settlement receipt header.
        resp = JSONResponse({"forecast": "sunny", "paid_by": result.payer})
        for k, v in result.response_headers.items():
            resp.headers[k] = v
        return resp
    ```

    ```bash
    SELLER_ADDRESS=0xYourSellerAddress uvicorn server:app --port 8000
    ```
  </Step>
  <Step title="Decode the 402 the way a client does">
    ```python title="decode.py"
    import httpx
    from circlekit.x402 import decode_payment_required

    resp = httpx.get("http://localhost:8000/forecast")
    print("status:", resp.status_code)

    x402 = decode_payment_required(resp.headers["payment-required"])
    option = x402.get_gateway_option()
    print("network:", option.network)
    print("price:", option.amount_formatted, "USDC")
    print("pay to:", option.pay_to)
    ```

    Run `python decode.py` in a second terminal. You should see `status: 402` and
    `price: 0.010000 USDC`.
  </Step>
</Steps>
````

Two things to notice here. First, the install line pins circlekit to a full commit
SHA, so every reader installs the exact version of the code the page was tested with.
Second, the page shows the expected output, so you can compare what you get with what
you should get.

The page asks for a `SELLER_ADDRESS`, the wallet that would receive the payment. Nothing
is paid in the Quickstart, so any valid address works; the script in step 5 uses
`0x000000000000000000000000000000000000dEaD`.

## 4. Describe the endpoint in OpenAPI

You then replace `openapi.yaml` with a description of the one endpoint:

```yaml
openapi: 3.1.0
info:
  title: Weather API (circlekit example)
  version: 1.0.0
servers:
  - url: http://localhost:8000
paths:
  /forecast:
    get:
      operationId: getForecast
      summary: Get the forecast (paid)
      description: >-
        Costs $0.01 in USDC. Without a valid PAYMENT-SIGNATURE header the server
        answers 402 with the payment requirements.
      parameters:
        - name: PAYMENT-SIGNATURE
          in: header
          required: false
          schema:
            type: string
      responses:
        '200':
          description: Payment settled. The body is the paid content.
        '402':
          description: Payment required, or the payment was rejected.
```

And validate the project:

```bash
npx --yes @thallylabs/cli@latest check
```

This checks frontmatter and most links (step 2 lists the ones it
missed). You should see `No issues found.`

## 5. Run the code blocks

`thally check` (the checker you ran in steps 2 and 4) tells you the pages are well formed.
It cannot tell you if the Python in
them works. For that, I wrote a short script that finds every code block with a
`title="..."`, writes it to a file of that name, and refuses to continue if two blocks
with the same title disagree. You can save it as `tools/extract_blocks.py`:

```python
"""Write every code block that has title="name" in the MDX pages to WORKDIR/name."""
import pathlib
import re
import sys
import textwrap

BLOCK = re.compile(r'^([ \t]*)```\w+ title="([^"]+)"\n(.*?)^\1```', re.S | re.M)


def main(content_dir, workdir):
    found = {}
    for page in sorted(pathlib.Path(content_dir).rglob("*.mdx")):
        for _indent, name, body in BLOCK.findall(page.read_text()):
            code = textwrap.dedent(body)
            if name in found and found[name][1] != code:
                sys.exit(f"conflicting blocks for {name}: {found[name][0]} and {page}")
            found[name] = (page, code)
    out = pathlib.Path(workdir)
    out.mkdir(parents=True, exist_ok=True)
    for name, (page, code) in found.items():
        (out / name).write_text(code)
        print(f"extracted {name} from {page.name}")


if __name__ == "__main__":
    main(*sys.argv[1:3])
```

You also need a script that installs circlekit with the exact command from the page,
starts the server, and runs the client. The script works in `../docsrun`, a folder next
to the project, so the extracted files never mix with your site. Save it as `tools/run_quickstart.sh`:

```bash
#!/usr/bin/env bash
# Extract the Quickstart's code, install circlekit as the page says, and run it.
set -eu
WORK="${1:-../docsrun}"
python3 tools/extract_blocks.py src/content "$WORK"
INSTALL=$(grep -m1 -oE 'pip install "circle-titanoboa-sdk[^"]+"' src/content/quickstart.mdx)
cd "$WORK"
python3 -m venv .venv
eval ".venv/bin/$INSTALL" -q
SELLER_ADDRESS=0x000000000000000000000000000000000000dEaD \
  .venv/bin/uvicorn server:app --port 8000 > server.log 2>&1 &
SERVER=$!
trap 'kill $SERVER' EXIT
for _ in $(seq 30); do curl -s -o /dev/null localhost:8000/docs && break; sleep 1; done
.venv/bin/python decode.py
```

Run it:

```bash
bash tools/run_quickstart.sh
```

The installation takes around one minute. When it finishes you should see these lines
(pip may also print a notice about a newer pip version):

```text
extracted server.py from quickstart.mdx
extracted decode.py from quickstart.mdx
status: 402
network: eip155:5042002
price: 0.010000 USDC
pay to: 0x000000000000000000000000000000000000dEaD
```

For the circlekit docs website, I used the same process for the
payment guide too. The script that runs the guide's code also takes a testnet private key
from a file, deposits test USDC into Gateway (the buyer pays from that balance), and pays
the endpoint, so the guide's
expected output (`status: 200`, a Gateway balance that drops by 0.01) comes from an
actual run. That script is not in the site repository, because it handles a key file;
the two scripts above are all you need to repeat the idea.

## 6. What running the docs found

Now, the interesting part. The first time I ran the payment guide's code with a funded test wallet, the payment
failed:

```text
httpx.HTTPStatusError: Payment failed with status 402
```

There was no reason in the message. The SDK's unit tests passed, and the code matched
the README. Later, I found that the SDK hid Gateway's reason in two places: the seller's
middleware replaced it with a generic "Invalid payment signature", and the buyer's error
message left out the response body.

What changed was outside the repository. To pay, the buyer signs an authorization that
lets Gateway move its USDC until an expiry time. circlekit set that expiry 4 days ahead,
and Circle Gateway required at least 7.

I confirmed it in two ways. First, I sent authorizations with different lifetimes to
Gateway's verify endpoint: 4 and 6 days were rejected with
`authorization_validity_too_short`, and 7 days was accepted. Second, I compared versions
of Circle's own npm package, `@circle-fin/x402-batching`: 3.0.0 sets a 4-day window, and 3.0.4 sets a 7-day minimum.

This bug meant that a seller and a buyer on circlekit's default settings could not
complete a payment on Arc Testnet, and nothing in the repository showed it. The fix,
which signs for at least 7 days plus a 100-second buffer, went to the SDK's repository as
[vyperlang/circle-titanoboa-sdk#5](https://github.com/vyperlang/circle-titanoboa-sdk/pull/5).
I then changed the pinned commit on the pages to the merge commit, ran the docs again,
and the guide's payment returned `200`. The fix also passes Gateway's reason through to
the buyer, and the guide's troubleshooting section now shows that format, copied from a
run where I made the buyer pay its own address:

```text
httpx.HTTPStatusError: Payment failed with status 402: {"error":"Payment verification failed","reason":"self_transfer"}
```

This is why I think docs should be runnable. A docs page is often the only place where
all the moving parts of a project meet. Here they were the SDK, the payment service, the
testnet, and the reader's shell. With so many layers, one part can change and break the
others, and users lose a working service because a dependency changed underneath it.
Pinning the version alone would not have caught this, because the service changed, not
the code. Running the pinned pages is what caught it. This matters more as people build
with AI coding tools: those tools copy what the docs say, so correct docs let users
build with your technology faster.

## 7. Preview, build, and check the links

It helps to see the site while you write. The project's `npm run dev` script serves it
at `http://localhost:3040`. To build the site and serve the build, use `npm run build`
and then `npm start`.

Before you publish, run the checks that the scaffold's `AGENTS.md` file lists: `check --ci`
with the CLI version pinned in the project, `npm test`, and `npm run build`. The `@latest`
CLI used in this article can be newer than that pinned version.

If you are on an older Linux, read this before running `npm run build`. On Ubuntu 20.04,
the build failed for me with only `Error: write EPIPE`, on my content and on an untouched scaffold. The cause
is a call near the top of `next.config.ts`, `initOpenNextCloudflareForDev()`. It starts
Cloudflare's `workerd` runtime, and that binary needs a newer glibc than 20.04 ships.
`npm run dev` loads the same file. I did not confirm whether it fails the same way, but
the workaround below gives you a local preview either way. The hook is there for
Cloudflare bindings during local development, so for a local preview you can work in a scratch copy with that one line
commented out:

```bash
rsync -a --delete --exclude .next ./ ../preview/ && cd ../preview
sed -i 's/^initOpenNextCloudflareForDev()/\/\/ &/' next.config.ts
npm run build && npm start
```

Leave the line in the copy you publish. After each content change, stop the running
`npm start` (Ctrl+C, it holds port 3040), go back to the project directory and run all
three lines again: the `rsync` copies the original `next.config.ts`
back, so the `sed` has to follow it. Use `npm run build`, not `npx next build`: its
`prebuild` script regenerates the compiled pages, and without it the server shows the old
ones. `npm start` serves on port 3040.

Since `thally check` missed links in step 2, check the built site too. With `npm start`
running, run this in a second terminal. It prints the status of each internal `<a href>`
in the server-rendered HTML of every page in `/sitemap.xml`. It can miss links that only
render in the browser, such as parts of the sidebar, and it does not check images:

```bash
B=http://localhost:3040
for p in $(curl -s $B/sitemap.xml | grep -o '<loc>[^<]*' | sed 's#<loc>https\?://[^/]*##'); do
  curl -s "$B$p" | grep -o '<a [^>]*href="/[^"#]*' | sed 's/.*href="//'
done | sort -u | while read -r h; do echo "$(curl -s -o /dev/null -w '%{http_code}' "$B$h") $h"; done
```

Every line should start with `200`, apart from `307 /api`, a redirect to the API overview.

## What you get without extra work

Every Thally site also serves:

- `/llms.txt` and `/llms-full.txt`, an index and full text for language models,
- each MDX page as Markdown or JSON (`?format=md`, `?format=json`; in my build the
  generated API operation page returned `404` for both),
- a read-only [MCP](https://modelcontextprotocol.io) server at `/api/mcp`, which AI tools can use to search and read the docs,
- `/openapi.json` and `/openapi.yaml` from the spec in step 4.

These came with the starter; I did not configure any of them.

## Summary

In short, to get a docs site running with Thally and keep it from drifting away from the code, here is what I did:

- Scaffold with `create-thally-docs`, then edit only `src/content/`, `docs.json`,
  `src/data/site.ts` and `openapi.yaml`.
- Give every code block that becomes a file a `title`, pin the SDK version on the page,
  and run the pages. `thally check` covers structure; it cannot tell you the code works,
  and it misses some links.
- When a run fails, fix the cause where it lives. For circlekit, that meant a pull request
  to the SDK, then a new pin and another run.
